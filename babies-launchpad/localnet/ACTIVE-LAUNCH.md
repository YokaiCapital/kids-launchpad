# Separate long-lived v3 localnet campaign

This service is isolated on `127.0.0.1:19099`. The local application's default prelaunch API now selects this v3 campaign. The original v1 registry and refund-only routes remain available through the legacy escrow disclosure. No mainnet execution is available.

From `babies-launchpad`:

- `node localnet/provision-active-launch.mjs` resumes or creates one persistent campaign with a 24-hour commitment period and a further 24-hour launch window. Terms are 100 SOL soft cap / 500 SOL hard cap at the local $200/SOL reference, 1B tokens with six decimals, and 43.5% prelaunch / 43.5% liquidity / 10% parents / 3% dev.
- `node localnet/verify-active-launch.mjs` executes one **0.001 test-SOL** commitment and checks replay, ownership and tampering rejection. Re-running adds another test commitment.
- `node localnet/launch-active.mjs` runs only after funding closes: finalize, settle receipts, return excess, then create and lock the pool atomically. Below-soft-cap or timed-out campaigns do not launch. `settleActive()` can be called separately for full-refund recovery.
- `node --test localnet/test/active-launch.test.mjs` checks cap/refund math and registry/receipt rejection.

`readActive(owner)`, `prepareActive(owner,input)` and `submitActive(owner,input)` mirror the existing escrow service shapes. Preparation takes `action`, a unique `requestId` and `amountLamports` for a commitment. Submission accepts the prepared `intentId` and either an exact external signed transaction or `local:true` for the existing Alice/Bob test identities. The service persists signed bytes before sending and returns the original receipt on retry; ambiguous sends are never rebuilt until definitive failure or finalized expiry.

Provisioning puts the complete fixed supply in the launch authority PDA's token account and gives it mint/freeze authority. The sponsor separately funds 0.3 test SOL for setup. The two existing verified parent test mints are snapshotted at finalized commitment; immutable parent configuration is included in the same transaction as campaign initialization, before commitments are possible. Publisher snapshot trust remains explicit.

The registry, setup keypairs, parent proofs, transaction intents and operator journal are stored only in ignored `.runtime/` files. The registry pins the ledger, program identity and verified binary. A program upgrade or ledger reset fails closed rather than silently attaching old commitments to another deployment. This file does not authorize replacing that registry or deleting records.

Verification completed: seven unit tests, eight actual service checks, fresh-process persisted replay, and rejection of operator launch while funding remains open. The long-lived campaign's after-close operator path is implemented but has not been executed against this 24-hour campaign; the canonical atomic launch builder is separately qualified by the existing launch harness. External wallet claim signing and active post-launch state/claim/trade selection are implemented (see CLAIM-SIGNING.md), gated on confirmed phase 3. The still-open active campaign has not exercised that transition end to end. Fee counters bind to the selected campaign; automatic active fee operation and production qualification remain separate integration work. Run one service writer per runtime directory; the local JSON intent store is not a distributed transaction database.

The local Admin overview includes **Launch local pool**. This fixed operator action is guarded by the on-chain close time and runs asynchronously; it exposes no arbitrary shell command or caller-selected campaign. Signed transaction bytes and lookup-table setup are retained in the operator journal for recovery. The button cannot bypass the funding deadline or launch a below-soft-cap campaign.

Current combined verification: 20 localnet unit tests, 3 trade tests, 44 frontend/gate checks and 18 Rust unit tests passed; actual-chain harnesses passed 26 launch/claim, 9 fee, 5 failure/recovery, 8 active-service and 6 trade checks. These checks are bounded local validation, not an independent security audit or production certification. The private hosted preview is separate from the local operator backend. Production still requires a persistent authenticated backend, independent review, verified real parent mints and snapshot governance, price-source rules, monitoring, and explicit mainnet release qualification.

## Automated lifecycle and durable operator recovery

The account service now runs `createActiveLifecycleKeeper` every 15 seconds. It reads the registered v3 localnet campaign, leaves open funding untouched, settles closed campaigns and invokes the existing atomic pool launcher only after all receipts are settled above the soft cap and before the launch deadline. Failed and expired campaigns follow the full-refund path. The keeper rechecks campaign identity and chain time after settlement. Independent leases and settlement single-flight prevent overlapping writes within the required single API writer.

Both launch and settlement operators retain signed transactions in separate durable journals. Every broadcast, including a retry after disk failure, is preceded by a successful durable write. An absent transaction is replaced only after finalized block-height expiry; finalized execution failures are archived before replacement. Refund operation identities include the amount already refunded, so an earlier excess refund cannot suppress the remaining full refund after launch timeout.

`node localnet/qualify-active-lifecycle.mjs` creates disposable registries and distinct short-funding-window campaigns on the existing isolated local validator, using the actual provisioner, commitment service, keeper, atomic launch and claim adapters. It leaves the original active campaign files unchanged. It shares and funds the existing local test wallets; it is not a mainnet tool, a separate-ledger restore drill, or a public browser wallet test. Public receipt evidence is written to ignored `.runtime/active-lifecycle-qualification.json`; temporary copied keys are removed afterward.
