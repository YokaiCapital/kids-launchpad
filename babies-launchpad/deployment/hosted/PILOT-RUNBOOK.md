# Private pilot runbook: one Standard v3 launch behind the owner's wallet

Written 27 September 2026 for the owner, updated 28 September 2026. Status: code on `feature/public-launches`, tested
locally and rehearsed on isolated ledgers; the version-3 program is deployed on mainnet (an upgrade is pending, step 2);
no hosted service exists yet. Shartcoin and its services (`kids-api` legacy routes and keepers, `kids-signer` build 6,
`believers-worker`) are not changed by any step here.

## What the pilot is

- Public launches on the version-3 program, on mainnet, reachable only by one wallet
  (`KIDS_PUBLIC_PILOT_WALLET`, also sealed into the program as the only creator). Everyone else sees nothing new.
- One image, several services, chosen by `KIDS_ROLE`: the existing API (unset), the version-3 signer (`signer-v3`),
  one worker per lane (`worker`), the indexer (`indexer`) and the pilot API (`api-pilot`).
- Every hosted process proves the release manifest against the chain and the shared registry before it does anything,
  and refuses to start on a mismatch. Every hosted process answers `/healthz` and `/readyz` on `PORT` for the platform.

- The GitHub readiness monitor (every 15 minutes, on `main`) also checks the pilot API once the repository variable
  `KIDS_PILOT_API_BASE` is set to `https://<pilot api domain>`; it opens an issue and posts to the same webhook on
  failure (workflow `KIDS readiness`).
- The creator operations panel of a fresh draft shows the sealed economics from the manifest and the
  "Private pilot (1 to 5 SOL)" preset.

## 7. The full launch, through the UI

1. Create the coin with the "Private pilot (1 to 5 SOL)" preset. One click, one wallet approval: the transaction
   creates the token, its custody, the campaign, the setup budget and the operating reserve (0.1 SOL). The page says
   "Your coin is created" once the transaction is confirmed; the records finish by themselves. (While the release file
   still names build `71d0d62c…`, the older path runs instead: four approvals, mint, custody, campaign, reserve.)
2. On the schema-40 creator release, the server continues after the single approved transaction, registers finalized
   evidence, credits the reserve and schedules the existing restricted keeper automatically. The coin page distinguishes
   confirmed creation from funding readiness. `zsh babies-launchpad/deployment/hosted/pilot-operator.sh status --campaign
   <address>` remains the read-only check. If automatic activation pauses, use the saved request's one Retry button;
   do not create a replacement campaign. Older/manual campaigns retain the explicit `grant-keeper` and `schedule` tools.
3. Commit from your wallet until the soft cap is reached inside the two-hour window.
4. After the window: settlement, launch (pool created, liquidity locked), excess refunds and fee setup run from the
   workers; the coin page shows the live pool.
5. Claim your tokens and any excess refund from the coin page; trade once so fees exist; the harvest and distribution
   jobs collect and pay the treasury and dev shares.
6. The creator operations panel shows the reserve spent, available now, pending refills; the `low-operating-reserve`
   alert fires below the 0.02 SOL floor.

## 8. The failed launch

Create a second coin, commit less than the soft cap, let the two windows expire. Refunds run by themselves; then
`zsh babies-launchpad/deployment/hosted/pilot-operator.sh grant-return --campaign <address>` gives the unused reserve
back to the creator wallet.

## 9. Stopping

Remove `KIDS_CREATOR_FLOW` and `KIDS_RELEASE_MANIFEST` from the pilot API and redeploy: the public routes go dark. Stop
the worker, indexer and signer services. Shartcoin keeps running on the unchanged services.

## 10. Backup and restore drill of the pilot database

`zsh babies-launchpad/deployment/hosted/pilot-registry-drill.sh` runs the drill inside the platform (through
`railway ssh` on the accounting worker's container, since the database has no public address): one consistent
`pg_dump` over the private network, a restore into a new throwaway database on the same server, never inside the live
database, a comparison of every table's fingerprint, the schema check against the release, then the throwaway database
is dropped and a report with sizes and times is printed (`--keep-archive` keeps the dump in the container's private
temp folder, which vanishes with the container). The same tool is tested in CI against a migrated schema
(`localnet/hosted/registry-drill.test.mjs`). Railway's own daily backups are the second copy; restoring one of those is
a dashboard action and needs the chain reconciliation described in `deployment/RECOVERY.md` before writes reopen.

## Signer key incident and audited job recovery, 28 September 2026

What happened: the hosted signer had loaded its key into a buffer that it then wiped, and the wallet library keeps that buffer,
so every signature was made with a zeroed secret. The signer's own check refused each signature before storing it, so no money
moved, but the first settlement failed after eight retries. Fixed in 34dd960 (key copied; deterministic refusals answer 409 and
stop retries; database or timeout failures keep the retry path). Evidence: `deployment/evidence/A38-SIGNER-KEY-FIX-2026-09-28.md`.

If a job is `failed` and the cause is fixed, recover it with the audited command (it refuses if anything changed):

Step 1, look (changes nothing):

```
zsh deployment/hosted/pilot-recover-job.sh --job <job id> --reason <reason> --recovery-id <unique id> --dry-run
```

Give `--actor <your name>` on the dry run; it is copied into the printed command. The dry run prints a `before` line (the
row as it is now) and an `invocation` line: the complete write command (`zsh deployment/hosted/pilot-recover-job.sh …`) with
the reviewed token, result hash, scope and actor filled in. Step 2, run that printed command exactly as printed, from the
repository root; do not add flags to it (a duplicated flag is refused).
The write refuses if the row changed since you looked; then look again. Expected output of the write: `before`,
`recovery` with `"requeued":true`, `after` with state queued. A `refused` line comes with a non-zero exit status: stop and
report it. Reasons: `transient-retry-reviewed`, `reconciliation-budget-correction` (a settlement whose packets expired
unsigned), `expired-grant-regranted`, `activity-decoder-fix-reviewed`.

The same command repairs an accounting `operating-refill` row that was queued without its payer/policy binding (rows
seeded before 28 September 2026 never get leased): `--action bind-refill --job <job id> --recovery-id <unique id> --dry-run`,
then the printed write command. The binding comes from the campaign's verified fee activation; nothing else on the row
changes. The command needs the Railway CLI on your Mac (it runs inside the accounting worker); the deployer session's tool
policy cannot run it for you.
